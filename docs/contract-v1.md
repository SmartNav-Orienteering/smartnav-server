# SmartNav App–Server Contract v1

Draft, 27 September 2026 · Geoff Hudson

## Overview and conventions

The v1 contract consists of two JSON documents: the **course package** (server to app) and the **submission** (app to server). The app uses the package to run the activity offline. The server scores every submission from its raw track, so scoring rules can change without an app release.

**Paper map is mandatory.** Participants navigate with a printed map that carries control descriptions, point values and course notes. The package therefore carries only what the app needs to detect punches and time the run.

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/v1/events` | GET | List open events (optional when onboarding by QR code) |
| `/v1/events/{event_id}/package` | GET | Download the course package; supports `ETag` / `If-None-Match` |
| `/v1/events/{event_id}/submissions` | POST | Upload a completed or abandoned run |
| `/v1/submissions/{submission_id}/result` | GET | Fetch the scored result for one run |
| `/v1/events/{event_id}/results` | GET | Public results for the event, so the app can show the results list |
| `/v1/submissions/{submission_id}/track` | GET | Public track for one run, so the app can display it |

**QR onboarding.** The event QR code encodes `smartnav://join?server=https://club.example.org&event=2026-10-harcourt-hill`. The app fetches the package from that server.

**Conventions**

- Transport: HTTPS only, JSON in UTF-8, gzip accepted in both directions.
- Coordinates: WGS84 decimal degrees, 6 decimal places (about 0.1 m).
- Distances in metres, durations in seconds (fields ending `_s`), except course time limits and alerts, which are in whole minutes (fields ending `_min`).
- Timestamps: RFC 3339 in UTC with milliseconds, e.g. `2026-10-04T00:12:03.250Z`. The event's local time zone is carried separately for display.
- Control codes are strings (`"31"`, `"S"`, `"F"`), because clubs use leading zeros and letters.
- `submission_id` is a UUIDv4 generated by the app. This makes uploads safe to retry.
- Each document starts with `format` and `format_version`. Additive changes keep the version, and the app must ignore unknown fields. Breaking changes move to `/v2/`.

## Components

The solution is built as five user-facing components plus the supporting pieces that make it installable, testable and safe to run. The phone app and the host talk only through the API defined in this contract.

**User-facing components**

| # | Component | Used by | What it does |
| --- | --- | --- | --- |
| 1 | Admin site | Owner and delegates | Create, edit, publish and delete events. Organise events into folders and series. Import controls (code, lat, long) from KML, as exported by the course-design tool. Import a KMZ map image with its corner coordinates, used as the background for track replay. Set the event type and its host-only scoring parameters. Generate the event QR code and link for the paper map |
| 2 | Event API: list and download | Phone app | `GET /v1/events` and `GET /v1/events/{event_id}/package`. Returns open events and the course package. Not a page people visit |
| 3 | Submission API and scoring | Phone app | `POST /v1/events/{event_id}/submissions`. Stores the raw run, re-detects punches from the track and scores it with the event's plugin. Returns the result via `GET /v1/submissions/{submission_id}/result` |
| 3a | Web upload page | Participants | Backup route: upload a GPX file from a watch or another app when the phone app failed. Scored the same way as an app submission |
| 4 | Results site | Public and participants | Results table for each event and each series, with age class rather than year of birth. Leg splits. Track replay over the KMZ map for one or more participants, to compare routes |
| 5 | Phone app (iOS and Android) | Participants | Join an event by QR code or from the list. Enter name, club and year of birth, and accept that the name, result and track will be public. Start by reaching the start circle or tapping Start (tap is used for mass starts). Record the track, beep at controls, record the finish. No manual punching: the participant never needs to handle the phone on course. Save the run on the phone, upload with automatic retry, show the result once scored, and view event results and other participants' tracks |

**Supporting components**

| Component | What it covers |
| --- | --- |
| Scoring plugin SDK | `smartnav-sdk`: base classes, data types (`Course`, `Track`, `Punch`, `Result`) and a test harness. The hooks clubs use to define their own event types |
| Built-in plugins | `line`, `score` and `scatter`, written against the SDK so they also serve as examples. Series scoring (e.g. a season league table) uses the same plugin approach |
| Accounts and roles | Logins for the owner and delegates, with permissions such as manage events, review results or view only |
| Organiser review tools | Queue of runs marked `needs_review`. Track view with each control's circle, so the organiser can accept or deny individual controls the GPS missed or doubtfully recorded. Disqualify a run, or rescore an event after a course or plugin fix. Every change is logged with who made it and why |
| Results export | CSV and IOF XML for club websites and state associations |
| Test tools | Track simulator that replays sample GPS tracks through punch detection and scoring, so courses and plugins can be checked without going out to run |
| Installation package and guide | Docker image and compose file, `pip` install route, HTTPS setup (Caddy or Cloudflare Tunnel), automatic backups, and a short guide for club volunteers |
| Privacy settings | Tracks and results are kept indefinitely and are public in the app and on the results site. The app states this before the first run and records the participant's acceptance. Year of birth is used only to derive age class and is never published |
| App store publishing | Apple developer account (about US$99 a year) and Google Play account (US$25 one-off), store listings, and the background-location explanation Apple review requires |

Year of birth is collected through `participant_fields`; the host maps it to an age class using the club's own class rules, so the phone never needs those rules.

## Course package format

The package holds everything the app needs to run a course with no signal: controls, punch radius, start and finish behaviour, time limit, and which details to ask the participant for. The app knows nothing about scoring. It only needs to know whether controls are ordered, and what to show.

| Field | Type | Req. | Meaning |
| --- | --- | --- | --- |
| `format` | string | yes | Always `"smartnav.package"` |
| `format_version` | integer | yes | `1` |
| `package_hash` | string | yes | `sha256:` of the canonical JSON with this field removed; changes whenever the course changes |
| `event.id` | string | yes | Server event ID used in URLs |
| `event.name`, `event.club` | string | yes | Display text |
| `event.opens_at`, `event.closes_at` | timestamp | yes | Window in which a run may start |
| `event.timezone` | string | yes | IANA zone for display, e.g. `Australia/Sydney` |
| `event.info_url` | string | no | Web page with event notes and safety info |
| `server.submit_url` | string | yes | Absolute URL for the submission POST |
| `course.event_type` | string | yes | Server plugin ID: `line`, `score` or `scatter`; display only on the phone |
| `course.ordered` | boolean | yes | `true`: the app punches only the next control in sequence. `false`: any control, any order |
| `course.time_limit_min` | number | no | Time limit in whole minutes, typically 60 for a score course. The app counts down and sounds the alerts, but keeps recording past the limit until the finish punch; the host applies late penalties |
| `course.start` | object | yes | `code`, `lat`, `lon`, `mode` (`punch` = start on reaching the start circle, `tap` = start button) |
| `course.finish` | object | yes | `code`, `lat`, `lon`, `mode` (`punch` or `tap`) |
| `course.controls[]` | array | yes | Per control: `code`, `lat`, `lon` |
| `course.punch_radius_m` | number | yes | One punch radius for the whole course, applied to every control, start and finish; 15 m suggested |
| `punching.max_accuracy_m` | number | yes | Ignore fixes worse than this for punching; 25 m suggested |
| `punching.repunch_cooldown_s` | number | yes | Suppress repeat beeps for the same control |
| `recording.interval_s` | number | yes | Target GPS sample interval; 1–2 s suggested |
| `recording.max_duration_s` | number | yes | Hard stop so a forgotten phone does not record all day |
| `alerts[]` | array | no | Warnings before the time limit, e.g. `{ "before_limit_min": 5, "sound": "long" }` |
| `participant_fields[]` | array | yes | Details the app asks for: `key`, `label`, `required`, optional `options` |

**Score course configuration (host only).** The organiser assigns point values to controls on the host when setting up a score event. They are stored in the event's scoring configuration and read by the `score` plugin. They are never included in the package, because the phone does no scoring.

```json
{
  "event_type": "score",
  "params": {
    "points": { "41": 10, "52": 20, "63": 30 },
    "default_points": 10,
    "late_penalty": { "per_started_minute": 10 },
    "disqualify_after_min": 30,
    "finish_required": true
  }
}
```

| Parameter | Meaning |
| --- | --- |
| `points` | Points for each control code |
| `default_points` | Used for any control not listed in `points`; optional |
| `late_penalty.per_started_minute` | Points deducted for each started minute over `course.time_limit_min`, measured from start to the finish punch |
| `disqualify_after_min` | Minutes over the limit after which the score is zero; optional |
| `finish_required` | Whether a run without a finish punch scores zero |

The host validates this configuration against the course when the event is published: every control code must exist on the course, and points must be whole numbers of 0 or more.

**Scatter course.** The participant must visit a specified number of the course's controls, in any order, and then return to the finish. Fastest elapsed time wins. The package is the same as a score course except for `event_type`, and it normally has no time limit. The required number of controls is printed on the paper map and held only on the host.

```json
"course": {
  "event_type": "scatter",
  "ordered": false,
  "time_limit_min": null,
  "punch_radius_m": 15,
  "start":  { "code": "S", "lat": -35.231020, "lon": 149.082310, "mode": "tap" },
  "finish": { "code": "F", "lat": -35.231020, "lon": 149.082310, "mode": "punch" },
  "controls": [
    { "code": "41", "lat": -35.227300, "lon": 149.086010 },
    { "code": "52", "lat": -35.224880, "lon": 149.080770 },
    { "code": "63", "lat": -35.233640, "lon": 149.077450 },
    { "code": "74", "lat": -35.229140, "lon": 149.076200 }
  ]
}
```

**Scatter course configuration (host only)**

```json
{
  "event_type": "scatter",
  "params": {
    "controls_required": 3,
    "finish_required": true
  }
}
```

| Parameter | Meaning |
| --- | --- |
| `controls_required` | Number of different controls that must be visited before finishing |
| `finish_required` | Whether a run without a finish punch is a non-finisher |

Scoring rules:

- A run is complete when at least `controls_required` different controls are punched before the finish punch. Complete runs are ranked by elapsed time from start to finish.
- Controls visited beyond the required number are recorded but neither help nor penalise.
- A run with too few controls is marked mispunch (`MP`) and not ranked; the result lists the controls that were counted.
- If `course.time_limit_min` is set, complete runs over the limit are marked over time (`OT`) and not ranked.

When the event is published, the host checks that `controls_required` is at least 1 and no more than the number of controls on the course.

## Submission format

A submission carries the raw track and the punches the phone detected. The server treats the phone's punches as evidence, not as the answer: it re-detects punches from the track and scores those.

| Field | Type | Req. | Meaning |
| --- | --- | --- | --- |
| `format`, `format_version` | string, integer | yes | `"smartnav.submission"`, `1` |
| `submission_id` | UUID | yes | Generated once per run; the retry key |
| `event_id` | string | yes | Must match the URL |
| `package_hash` | string | yes | Package the run used, so the server scores against the right course version |
| `participant` | object | yes | Values for each `participant_fields` key |
| `device` | object | yes | `install_id` (random UUID per app install), `platform`, `os_version`, `app_version`, `model` |
| `activity.started_at`, `activity.ended_at` | timestamp | yes | Start and end as the phone saw them |
| `activity.start_method` | string | yes | `punch` or `tap` |
| `activity.end_reason` | string | yes | `finish_punch`, `finish_tap`, `max_duration`, `abandoned` |
| `punches[]` | array | yes | Phone-detected punches: `code`, `t`, `lat`, `lon`, `accuracy_m`, `distance_m` (may be empty) |
| `track.epoch` | timestamp | yes | Time of the first point |
| `track.fields` | array | yes | Column order for `points`; v1 = `["dt_ms", "lat", "lon", "acc_m", "alt_m"]` |
| `track.points` | array | yes | One array per fix; `dt_ms` is milliseconds after `epoch`; `alt_m` may be `null` |
| `app_log[]` | array | no | Short diagnostic strings (GPS lost, app backgrounded), max 200 |

The track uses compact arrays rather than objects. An hour at 1 s sampling is about 3,600 points, roughly 150 KB of JSON and around 40 KB gzipped.

**Example**

```json

  "format_version": 1,
  "submission_id": "b7e3c0a2-6f1d-4c55-9a8e-2d41f0c9e7b3",
  "event_id": "2026-10-harcourt-hill",
  "package_hash": "sha256:9f2c…e41a",
  "participant": { "name": "Alex Citizen", "club_id": "4127", "category": "Open" },
```

**Upload and retry rules**

1. The app saves the finished submission to local storage before the first upload attempt, and deletes it only after a 2xx response.
2. It POSTs with `Content-Encoding: gzip`. On a network error, `408`, `429` or `5xx`, it retries with backoff (30 s, 2 min, 10 min, then hourly) and also retries when the app next opens.
3. The server keys on `submission_id`. A repeat POST of a stored submission returns `200` with the existing result link. A new one returns `201`.
4. On any other `4xx`, the app stops retrying and shows the server's `message`, keeping the file so it can be exported and sent to the organiser.

## Result response

The server returns pre-formatted display text generated by the scoring plugin, so the app can show a result for any event type without understanding it. Structured fields sit alongside it for the results page and future app features.

| `status` | Meaning | App behaviour |
| --- | --- | --- |
| `queued` | Received, not yet scored | Poll again after `retry_after_s` |
| `scored` | Final or provisional result available | Show `summary.headline` and `summary.lines` |
| `needs_review` | Scored, but flagged for the organiser (e.g. long GPS gap) | Show result with a "provisional" note |
| `rejected` | Not accepted (e.g. run outside event window) | Show `messages` |

**Example**

```json
{
  "format": "smartnav.result",
  "format_version": 1,
  "submission_id": "b7e3c0a2-6f1d-4c55-9a8e-2d41f0c9e7b3",
  "status": "scored",
  "provisional": false,
  "event_type": "line",
  "summary": {
    "headline": "29:44 — 4th of 27 (Open)",
    "lines": ["All 3 controls visited in order", "Fastest leg: 32 → 33 (4:12)"],
    "elapsed_s": 1784,
    "position": 4,
    "of": 27,
    "score": null
  },
  "controls": [
    { "code": "31", "status": "ok", "t": "2026-10-04T00:19:40.020Z", "split_s": 457 },
    { "code": "32", "status": "ok", "t": "2026-10-04T00:28:55.480Z", "split_s": 555 },
    { "code": "33", "status": "ok", "t": "2026-10-04T00:33:07.300Z", "split_s": 252 }
  ],
  "messages": [],
  "results_url": "https://club.example.org/events/2026-10-harcourt-hill/results"
}
```

Per-control `status` values: `ok`, `missed`, `out_of_order`, `late` (after time limit), `phone_only` (the phone beeped but the server could not confirm it from the track), `accepted` (credited by the organiser on review), `denied` (removed by the organiser on review).

## Validation, compatibility and errors

The server accepts anything it can safely score and flags the rest for review. A runner's result should never be lost because of a minor fault.

**Package versions.** The server keeps every published version of a package. A submission is scored against the version named by its `package_hash`. If the organiser has since changed the course, the run is scored against the old version and marked `needs_review`, never rejected.

**Server checks on each submission**

- `format_version` is supported and `event_id` matches the URL.
- Body is at most 10 MB after decompression.
- Track times increase, coordinates are in range, and the first and last points fall within `started_at` and `ended_at` (with a 60 s tolerance).
- The run started inside the event window. Runs that start early or late are held as `needs_review` rather than rejected, so the organiser decides.
- Gaps over 60 s in the track, or accuracy worse than `max_accuracy_m` for more than 20% of points, set `needs_review`.

**Error body.** Every non-2xx response uses one shape, and the app shows `message` as-is:

```json
{ "error": { "code": "event_closed", "message": "Entries for Harcourt Hill closed on 11 Oct at 6 pm." } }
```

| HTTP | `code` | When | App retries? |
| --- | --- | --- | --- |
| 400 | `invalid_submission` | Malformed JSON or missing required field | No |
| 400 | `unsupported_version` | `format_version` too new or too old; `message` says which app version is needed | No |
| 404 | `event_not_found` | Unknown `event_id` | No |
| 409 | `submission_conflict` | Same `submission_id` with different content | No |
| 410 | `event_closed` | Event deleted or archived | No |
| 413 | `too_large` | Body over the size limit | No |
| 429 | `rate_limited` | Too many requests from one install | Yes, after `Retry-After` |
| 5xx | `server_error` | Anything unexpected | Yes |

**Compatibility rules**

- The app ignores unknown fields in packages and results.
- The server ignores unknown fields in submissions and stores the full raw body, so later versions can reprocess old runs.
- New optional fields are added within v1. Renaming, removing or changing the meaning of a field requires v2 endpoints, and the server keeps serving v1 for at least one season.

## Decisions

| Topic | Decision |
| --- | --- |
| Repeat runs | A participant may run an event as often as they like. Every run is stored and published. When the event counts towards a series, only the participant's first run counts for the series |
| Manual punching | Not provided. Handling the phone on course costs time and is unsafe in urban terrain. The app only records the track; the organiser reviews doubtful controls and accepts or denies each one |
| Track retention and visibility | Tracks are kept indefinitely and are publicly visible in the app and on the results site |
| Mass starts | Supported with tap to start: all participants tap Start on the start signal |
